# 完整服务器架构

## 线程模型

服务器使用一个网络事件线程和固定数量的数据库工作线程：

```text
客户端
  │ TCP
  ▼
epoll 事件线程
  ├─ accept / recv / send
  ├─ 帧解码与 Protobuf 转换
  ├─ 玩家、聊天和 AOI 状态
  └─ 投递数据库任务
          │
          ▼
    有界任务队列
          │
          ▼
    数据库工作线程 ── MySQL / Redis
          │
          ▼
       完成队列 ── 写 eventfd ──► epoll 事件线程
```

只有事件线程修改在线玩家、AOI 和连接状态。数据库线程只操作仓储并产生值对象结果，因此不需要给整个游戏世界加锁。

## 网络处理

- 监听和客户端 socket 均为非阻塞模式。
- epoll 使用 LT 模式；每次可读通知都会循环 `recv`，直到返回 `EAGAIN`。
- 每个连接拥有独立的帧解码器和发送缓冲区。
- `send` 发生部分写或返回 `EAGAIN` 时保留剩余数据，并关注 `EPOLLOUT`。
- 单连接待发送数据默认上限为 4 MiB，超过后关闭慢连接，避免无限占用内存。
- 接收异常、协议错误、`EPOLLHUP` 和 `EPOLLRDHUP` 都会走统一连接回收流程。

## 登录与数据访问

1. 解析 `LoginRequest` 并校验账号。
2. 把玩家加载请求投递到有界数据库队列。
3. 不存在的账号生成玩家 ID、随机昵称和初始位置，再保存到 MySQL。
4. 如果客户端携带重连令牌，则从 Redis 加载并校验会话。
5. 写入带 TTL 的新会话后，结果通过完成队列和 eventfd 返回事件线程。
6. 玩家加入 AOI，收到自身和附近玩家信息；附近玩家收到进入视野事件。

断开连接后，玩家立即从在线表和 AOI 移除，当前位置异步保存到 MySQL。Redis 会话保留到 TTL 到期，使短时间内可以携带令牌重连。

## AOI消息规则

- `stayed`：向仍在视野内的玩家发送位置更新。
- `entered`：双方各收到对方进入视野消息。
- `left`：双方各收到对方离开视野消息。
- 世界聊天向全部在线连接广播，与 AOI 无关。

## 过载处理

- 数据库任务队列有容量上限；满载时立即拒绝，不阻塞 epoll。
- 单连接发送队列有字节上限；慢客户端积压超限后断开。
- 服务端设置最大连接数；超出限制的新连接会立即关闭。

这些策略的目标不是保证所有请求成功，而是在过载时保证服务器资源使用有明确上界。
